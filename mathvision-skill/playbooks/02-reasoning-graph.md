# 阶段 2:推理图(reasoning_graph)

> 提炼自平台的 `ExplorationPrompts`(概念图、解题图、模式判断)、`EnrichmentPrompts` 和 `SystemPrompts` 中的相关公共规则;归一化规则取自 `ExplorationNode`。
> 产物格式见 [../formats/knowledge-graph.md](../formats/knowledge-graph.md)。

## 这个阶段要解决什么

把题目变成一张**教学节拍图**:一串彼此有依赖的"讲解步骤"。阶段 3 会为**每个节点设计一个分镜场景**,所以这里划分节点的粒度,直接决定最终动画有几个场景、每个场景讲什么。

平台把这个阶段拆成两小步:

1. **探索**:规划图的结构(节点、边、教学顺序)。
2. **数学补全**:为每个节点补公式、符号定义、直观解释和例子,同时顺手纠正草稿里的数学错误。

两步的产物最终合并成同一份 `KnowledgeGraph`。

## 输入

- 阶段 1 的 ProblemBundle。它是**权威**:图里的每一句数学表述都不能和它冲突。

## 先判断:概念图还是解题图

读 ProblemBundle 的 `input_mode`。它已经是 `concept` 或 `problem` 时直接用,不用再判断。

- `problem`:要解的具体问题、证明、最值、练习。
- `concept`:要讲解的主题、定理、公式、想法。

两种图的节点类型不同(见下)。

## 第一小步:规划图

### 总体思路

- **用画面和运动建立直觉**:优先考虑具体的视觉情境、运动、变换、构造或对比。运动要服务两件事:让对象、条件和目标看得见;揭示真正关键的洞察。
- **运动不是必须的**:标注、公式、简短旁白、静态说明可以命名、总结或形式化已经可见的东西。不要为了给每个节点加动画而凑冗余节点。
- 避免:没有视觉锚点的纯文字堆砌;为显然的定义或简单等式单独做动画证明节点;近似重复的观察;不增进理解的装饰性运动。

### 解题图的推荐结构

适用时按这条线走:先搭建问题情境,让学习者看到对象、条件和变量 → 再用运动或操作揭示题目问的是哪个量、关系或目标 → 再给出关键构造或变换 → 最后是视觉化的结论,仅在有帮助时附一个简短对比。

- "搭建问题情境"和"揭示目标"是两个值得分开的节拍。例如先摆好点、线、路径,再拖动动点或扫过参数,观察目标量怎么变。
- 最短路径、极值、轨迹、角度或面积变化类题:优先用拖动、扫描、动态对比来揭示目标量如何变化。
- 辅助线、反射、旋转、平移、割补类方法:尽量让"为什么要这样构造"变得可视,但不要把每个直接推论都拆成单独的证明动画。
- 如果某个关系由构造直接保证(比如点关于直线对称后的等距),写进构造或变换节点里,不要单列节点。仅当它本身就是学习者的主要理解障碍时才拆出来。
- 起点是 depth 0 的"钩子"或"问题引入"节点,之后逐步走向最终结论。

### 概念图的推荐结构

- 从一个概念自然出现的具体视觉情境开始。
- 有帮助时,接一个独立的运动或操作节拍,揭示概念所刻画的关系、不变量或规律。
- 建立情境、运动揭示、正式命名这三件事,能分开就分开,让概念更容易被看见。
- 只在确实能增进理解时才加最后的对比节拍。

### 节点规则

1. 每个节点是**一个**清晰的教学节拍,只有一个核心要点。
2. `step` 里优先写学习者**看到什么在变化、做了什么操作**。如果某节拍只是必要的命名、总结或结论,就清楚地写出来,不要硬凑动画。
3. 关键洞察要明确出现,通过构造、变换、叠加、动态对比或简短说明呈现。
4. 显然的定义、等长等角、记号说明、由构造直接保证的事实,折进相关节点的措辞里,不单列节点。
5. 不要把真正不同的推理动作捆在一个节点里;也不要把一个自然连续的小推论过度拆碎。
6. 每个节点都必须直接服务于最终目标。

### 边规则

1. 只为**真正必要的前置依赖**连边,有帮助的背景不算。
2. 避免同义、近重复,以及父子重复。
3. 只有当前置观察、失败尝试或误解对理解后面的洞察是必要的,才把它们放进图。

### 节点类型

| 图 | 允许的 `node_type` |
| --- | --- |
| 概念图 | `concept`、`observation`、`construction`、`derivation`、`conclusion` |
| 解题图 | `problem`、`observation`、`construction`、`derivation`、`conclusion` |

### 坐标模型纪律(有 `coordinate_model` 时必看)

ProblemBundle 里的 `coordinate_model` 是硬约束,不是提示。

1. 先根据那些坐标、方程、范围、依赖公式推导解题路径,**再**写面向展示的步骤文字。
2. 变换、轨迹、最值类问题:在命名任何推导出的坐标、方程、有效弧段或极值点之前,先对固定中心和运动端点做简短的代入验算。
3. 用到变换后的对象时,只陈述与依赖公式一致的事实。不要把**中心的像**和**端点的像**混为一谈。
4. 如果 `ambiguities` 里来源图形已经选定了某个分支,整张图(包括所有推导出的坐标和最终数值)都要保持这个分支,不要换成"看起来更合理"的另一个。
5. 若坐标模型的公式与你的直觉画面或更短的题干冲突,**以坐标模型和分支选择为准**。

### 语言规则

- 面向学习者的字段(每个节点的 `step`、`reason`、`definitions` 的值、`interpretation`、`examples`)用**自然的中文**写。这是平台的约定,假设用户使用中文。若用户明确要求其他语言,按用户的来,并在整个产物里保持一致。
- 公式、变量名、点名、几何记号、LaTeX 保持符号形式,不要翻译成中文描述(如 `A`、`P`、`AB`、`x`、`\angle APB`)。
- **后端标识符保持 ASCII 英文**:节点 `id`、`start_node_id`、`node_type`、`next_edges` 的键和值、`teaching_order` 的条目。`definitions` 的键是被定义的符号本身。
- 标识符里若出现码位大于 0x7F 的字符(弯引号、长破折号、箭头、撇号、对勾、全角空格、Unicode 运算符),改写成 ASCII,并同步修正所有引用它的地方。

## 第二小步:数学补全

为**每个节点**补充下面这些字段(格式见格式文档):

| 字段 | 内容 |
| --- | --- |
| `equations` | 该步骤的关键公式,每条一个字符串,原始 LaTeX,**不带美元符号**,反斜杠按 JSON 转义;多行公式拆成数组的多项;紧凑且直接相关 |
| `definitions` | 图中或公式里**会出现的**符号、变量、几何对象、记号的简明中文含义。不要定义抽象概念、推理策略或教学方法 |
| `interpretation` | 学习者能听懂的简短直觉,解释公式意味着什么、为什么重要 |
| `examples` | 可选,能让解释更具体、又不会让未来的场景过载的例子 |

写作取向:

- **先讲为什么,再讲怎么做**;让公式感觉是被直觉"赚来"的,而不是孤立出现的符号。
- 只保留确实支撑后续视觉讲解的公式、定义和例子。**没有就留空数组或空对象,不要凑数。**
- 偏好直观解释和紧凑的符号支撑,而不是长篇教科书推导。默认的数学基础层次是初中数学。
- 不要发明另一条路线、额外的已知或没有依据的断言。
- 遇到合并多个前置分支的节点,把各分支的结论整合成一条延续,保持已建立的命名,不要从头重新讲。

### 在补全时必须顺手纠错

第一小步产出的图只是**草稿**,不是权威。补全每个节点时要核对它的 `step` 和 `reason`:

- 检查坐标写错、公式错、旋转或分支方向错、轨迹中心错、端点像错、极值错、漏撇号、下标错、变量互换、符号引用错。
- 一旦发现与 ProblemBundle 的题干、图形观察、`coordinate_model` 或已选定分支冲突,**以 ProblemBundle 为准**,直接改写 `step` 和 `reason`。
- 不要为了和前面草稿"连贯"而保留错误的坐标、方程、分支、轨迹中心、端点像、极值或最终数值。
- 之前的节点若有错误说法,后面的节点沿用**最新的、与 ProblemBundle 一致的**修正,不要重复旧错。
- 没有错就原样保留。**不要悄悄忽略错误**:这里修正后的文字会被所有下游阶段使用。
- 修正时直接改字段,不要写"这里有冲突"之类的解释。

## 你可以自己决定的事

- **节点数量与粒度**。节点数就是场景数。题目简单时 3 到 5 个节点往往够;复杂题可以更多。不要为了"完整"而堆节点。
- **补全是逐节点做还是一次做完**。平台是逐节点做的(每次只看一个节点,带最近若干轮上下文),好处是每一步专注、更容易发现该节点的错误。你可以合并,但合并后更要逐节点核对,不能偷懒跳过纠错。
- **要不要先让用户看图再补全**。图的结构一旦确定,后面全依赖它。结构拿不准、或题目有多种合理讲法时,先让用户确认结构再做补全,比做完再返工便宜。
- 平台对"补全失败的单个节点"的处理是保留原步骤、继续往下走。你同样可以对个别节点放弃补全,但要告诉用户哪些节点没补。

## 图的整理(落盘前自己做一遍)

平台会对图做归一化处理。你没有脚本替你做,落盘前要自己保证:

- 节点 `id` 统一小写、去首尾空格;重复的 id 只保留第一个;`step` 为空的节点丢掉。
- 边只在存在的节点之间,不要自环,不要重复。
- **起点**:必须是没有入边的节点。你指定的起点若有入边就不合法。多个候选时,优先选符合图类型的"入口"类型(概念图选 `concept`,解题图选 `problem`),其次 `observation`、`construction`、`derivation`、`conclusion`。若图里出现环、没有任何入边为零的节点,加一个人工入口节点(解题图 `problem_entry`,概念图 `concept_entry`),让它指向各候选起点。
- **`min_depth`**:从起点出发的最短边数。起点为 0。不连通的部分按顺序接在后面。
- **图必须无环**。平台不会替你检查环,有环会让教学顺序失去意义。
- **`teaching_order`**:列出每个节点恰好一次,且每个节点出现在它所有前置节点之后。
- `nodes` 是以 id 为键的**映射**(不是数组),起点字段叫 `start_node_id`,落盘前按 `min_depth` 再按 `step` 排序。规划和落盘用同一种格式,见格式文档。

## 完成的标准

- [ ] 每个节点是一个清晰的教学节拍,没有凑数节点,也没有把两件事塞进一个节点。
- [ ] 节点数符合你希望的场景数。
- [ ] 图无环,起点合法,`teaching_order` 覆盖全部节点且尊重依赖。
- [ ] 所有数学表述与 ProblemBundle 一致,`coordinate_model` 和已选分支被一路保持。
- [ ] 每个节点都核对过 `step` 与 `reason`,错的已改。
- [ ] 学习者可见文字是中文(或用户指定的语言),标识符是 ASCII。
- [ ] `equations` 无美元符号;`definitions` 只含图中或公式里会出现的符号。

## 给用户看什么

- **推理图**:用 Mermaid 流程图或缩进列表展示节点与依赖,标出起点和教学顺序。
- 每个节点一行:序号、类型、`step`,以及关键公式。
- 对你修正过的数学错误,简要说明改了什么。
- 明确告诉用户:**节点数就是动画的场景数**,请他们确认结构再往下走。

## 修改已有产物

用户提出修改意见时:把现有图当作修改基线,ProblemBundle 仍是数学权威;应用修改意见的同时保留无关的正确节点、教学顺序和图的连续性;返回**完整**的新图,不返回补丁。补全字段同理:对每个节点,基线里已有的补全内容,只改与修改意见有关的部分。

图的结构变了(增删节点、改顺序),分镜、代码必然失效,需要重做。只改某个节点的措辞或公式,则只需要检查并更新受影响的场景。
