# 阶段 1:题目规范化(problem_normalization)

> 提炼自平台的 `ProblemNormalizationPrompts`(生成与复核两套规则)和 `ProblemNormalizationNode`。
> 产物格式见 [../formats/problem-bundle.md](../formats/problem-bundle.md)。

## 这个阶段要解决什么

用户给你的输入形态各异:一段文字、一张截图、文字加图、附带的 md/txt 文件。后面所有阶段都不再看原始输入,只看这个阶段产出的 **ProblemBundle**。所以这一步要做到两点:

1. 把题目的数学含义**完整、忠实**地固定下来(题干、已知、所求、图形信息);
2. 判断两个会影响整条流水线走向的开关:`input_mode`(讲概念还是解题)和 `scene_mode`(2d 还是 3d)。

这一步**不解题**。解题思路是阶段 2 的事。

## 输入

- 用户的文字、图片、文本附件。多张图片可能分别承载题干、图形或两者。
- 用户是否已说明想要的呈现方式(默认 Manim 视频)。

## 推荐做法

平台分两遍做:先生成草稿,再拿草稿对照原始输入复核一遍。复核专门抓这几类错:识别或转写错误、漏条件、凭空添加的内容、标签或数值写错、`diagram.present` 判错、`scene_mode` 或 `input_mode` 判错。

你可以这样取舍:

- 输入是干净的短文字:一遍通常够,但交付前仍要自己逐条对照原文。
- 输入包含图片、手写体、多图,或题目带复杂图形:**建议做复核**,识别错误在这里最便宜,到了后面会被一路放大。
- 复核时要重新看图,不要只看自己的草稿。

## 规则

### 题干 `statement`

- 综合所有来源(文字加全部图片)合并成**一份**独立、完整的题干。
- 保持输入的语言,保持数学含义、变量名、标签、数量和所求目标。
- 不解题,不写解题推理;不加后续教学步骤、反思点、证明行、结论标记。

### `input_mode`

- `problem`:有具体的问题、证明、最值或练习要做。
- `concept`:要讲解一个主题、定理、公式或想法。
- 取最贴近操作的理解。

### `scene_mode`

- `2d`:平面几何、坐标图象、数轴、普通函数图象,以及一切不是非要深度不可的情形。
- `3d`:空间几何、三维坐标、立体、曲面,或推理确实需要深度。
- 拿不准选 `2d`。
- 它描述的是题目本身的维度,不是绘制顺序。图层先后后面用 `style.z_index` 表达。

### 图形 `diagram`

这是最容易出错的部分,核心原则是:**`diagram` 只记录"来源里亲眼看到的题目图形",不记录"根据文字可以画出来的图"**。

- 没有附带图片:`diagram.present = false`,即使文字里描述了点、线、图象、路径。
- 图片里只有印刷或手写的题目文字、公式、答案:`present = false`,这样的图是文字来源,内容归入 `statement`。
- 只有当图片里确实出现几何或图形内容(几何图形、函数图象、数轴、坐标图、视觉化的数学构造)时,才 `present = true`。
- `present = false` 时:`source_observed = false`,其余的描述字段用空对象或空数组。
- `present = true` 时:只描述题目**初始**图形,不描述未来的解答图。

`present = true` 时各字段的写法:

| 字段 | 内容 |
| --- | --- |
| `diagram_description` | 用自然语言按有意义的键分组描述所见图形,如 `overall_shape`、`points`、`segments`、`marks`、`regions`、`graphs`。用原生 JSON 对象和数组 |
| `coordinate_model` | 可选,但对几何或函数题强烈建议。当题干和图形足以建立一个简单数学模型时,给出坐标、方程、参数范围、依赖公式 |
| `unknowns` | 题目中的变量或目标量:动点、从属点、所求长度、面积、角度、极值 |
| `ambiguities` | 图形已经确定或尚未确定的分支选择:镜像、同侧或异侧、顺时针或逆时针、近交点或远交点、劣弧或优弧、内部或外部。凡影响数学结果或初始图形的都要记 |
| `normalization_notes` | 规范化过程的说明 |

补充要点:

- 如果来源图形确定了某个分支,在 `ambiguities` 里写明选了哪个,并在相关的描述或坐标依赖里重复一遍。这个选择会被后续阶段当作硬约束。
- `coordinate_model` 里写的坐标和公式,后续阶段会当作**硬约束**,不是参考。所以要先确认它们自洽,再写。
- 数学正确优先于像素级还原:原图画得不准时,只清理图中**已经出现**的初始图形,不要补推断出来的辅助构造。
- 不要使用分镜的对象结构或约束结构。这里只记录"证据",具体的对象 id 和结构化约束由阶段 3 创建。

### 不要做的事

- 不要从纯文字输入凭空造出一个 diagram。
- 不要添加原题图形里没有的辅助线、最优点、对称点、度量值或结论标记。
- 不要把图片里的文字当成图形。

## 你可以自己决定的事

- 一遍还是两遍(见上)。
- 题干有歧义或图片模糊到影响数学含义时,**直接问用户**,不要猜。猜错的代价是整条流水线白做。
- 用户同时给了多道题时,先和用户确认这次做哪一道,或者是否分别做。
- 旁白开关(是否需要语音讲解)可以在这里顺带问,也可以到阶段 3 前再问。它不属于 ProblemBundle,但尽早问清能避免后面返工。

## 完成的标准

- [ ] `statement` 与原始输入逐条对照过,没有漏条件、没有多出条件、标签与数值一致。
- [ ] 没有解题内容。
- [ ] `input_mode` 和 `scene_mode` 都已明确。
- [ ] `diagram.present` 与"是否真有图形"一致;`present = false` 时没有残留描述。
- [ ] 若有图形:动点、所求量、分支选择都已记录,`coordinate_model` 的公式可以代入验证。

## 给用户看什么

题干(完整)、你对图形的理解(一两句话加关键点)、`input_mode` 与 `scene_mode` 的判断及理由。有 `ambiguities` 时要点出来请用户确认,因为它会决定画面长什么样。

## 修改已有产物

用户提出修改意见时:以原始输入为数学依据,在不违背原始输入的前提下应用修改意见;保留无关的已规范化内容、标签、数量、图形事实、`input_mode` 和 `scene_mode`;返回**完整**的新 ProblemBundle,不返回补丁或说明。

修改了 ProblemBundle,通常意味着下游产物(推理图、分镜、代码)都可能失效。请告诉用户你打算重做哪些。
