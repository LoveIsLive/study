# MathVision 中期检查 UML 绘图规范调研

本轮以 PPT 中的组件图、活动图、类图、部署图、时序图为范围。规范依据为 [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/About-UML)，并对照 [规范原文 PDF](https://www.omg.org/spec/UML/2.5.1/PDF) 的 Notation 和 Semantics 小节。PlantUML 官方文档用于查渲染语法，符号含义以 OMG 规范为准。

五张图已按本调研结论完成第一轮修正；成功渲染只说明工具能解析源码，最终仍需结合论文语义和答辩版式复核。

## 1. 先确定图的用途与抽象层级

| 图 | 应回答的问题 | MathVision 中的建模对象 |
| --- | --- | --- |
| 组件图 | 哪些逻辑模块提供或使用哪些能力？ | 工作台、任务管理、编排、Agent 服务、模型适配、文件服务 |
| 活动图 | 一项业务如何流转、选择、循环和完成？ | 规范化、推理、设计、检查、确认、渲染和修复等行为 |
| 领域类图 | 核心概念有哪些属性和关联？ | 任务、任务版本、阶段产物、阶段结果 |
| 部署图 | 软件制品部署在什么计算节点和执行环境？ | 主服务与 Worker 主机、JVM、JAR、外部基础服务 |
| 时序图 | 某一具体场景中，参与者按什么顺序交换消息？ | Worker A/B、任务持久化服务、归档服务等交互角色 |

同一概念可以在不同视图中出现，但表达不同：Agent 可在组件视图中表示一个逻辑职责，在活动视图中通过它执行的行为出现；Worker 进程由运行环境承载，Worker JAR 是部署制品。

UML 核心规范没有一种可直接代替所有角色的“Agent 专用图元”。可以用组件、类、参与者或职责分区表达；若引入自定义构造型 «agent»，需要声明其含义及建模约定。

## 2. 通用线型与箭头

| 关系 | 标准记法 | 方向与含义 | PlantUML 常用表达 |
| --- | --- | --- | --- |
| 依赖 Dependency | 虚线＋开放箭头 | 使用方指向被依赖方 | A ..> B |
| 关联 Association | 实线 | 表达实例之间的结构关系；箭头可表达导航性 | A -- B；A --> B |
| 泛化 Generalization | 实线＋空心三角 | 子类型指向父类型 | Child --\|> Parent |
| 实现 Realization | 虚线＋空心三角 | 实现方指向契约或规格 | Impl ..\|> Contract |
| 共享聚合 | 实线＋空心菱形 | 菱形位于整体端，表示整体与部分关系 | Whole o-- Part |
| 组合 | 实线＋实心菱形 | 菱形位于整体端，具有强所有权与生命周期语义 | Whole *-- Part |
| 注释连接 | 虚线连接注释与元素 | 说明信息，不作为业务执行关系 | note ... end note |

注意：

- 相同线型放在不同图中可能表示不同模型元素，不能脱离图的类型解释。例如活动控制流、类关联与节点通信路径都使用实线，但语义不同。
- 关联箭头表示导航方向，不表示数据流或执行先后；未显示导航箭头时，也不能据此认定为双向导航。
- “保存了某条记录”不足以自动判断聚合或组合。共享聚合的精确语义由领域和建模者补充；组合需要明确整体、部分与生命周期约束。
- 颜色可突出关系，不能代替虚实线、箭头、守卫条件和关系关键字。

依据：§7.7.4 Dependencies、§9.2.4 Classifiers、§9.5.3 Properties、§11.5.4 Associations。工具表达参见 [PlantUML 类图文档](https://plantuml.com/class-diagram)；工具页面中的简化关系名称不能替代 OMG 关系定义。

## 3. 组件图

### 规范图形与连线

- 组件：矩形，带 «component» 关键字；显示标准组件图标时可省略该关键字。应能与普通类、动作区分。
- 接口：提供接口可画圆球，需求接口可画半圆插槽；也可用带 «interface» 的分类器矩形展开接口。
- 端口：组件边界上的小方块，表示一个交互点。
- 一般组件依赖：虚线开放箭头，使用方指向被使用方。
- 装配连接器：连接对应的提供／需求接口，使用实线连接；它与一般依赖不同。
- 显式接口实现：可用虚线空心三角从实现组件指向接口。

### 本项目布局约定

- 按“交互入口 → 业务与编排 → 执行及外部能力”组织主要阅读方向，支撑组件放一侧或下方。
- 图中保留逻辑依赖，数据库读写细节和具体调用先后放到相应的其他视图。
- 数据持久化能力若出现在严格组件图中，用组件／接口及名称说明，不直接以数据库圆柱充当 UML 组件。
- 一个概览图可只展示组件和依赖；不必为了形式完整，为每条调用虚构端口和接口。

### 本次修正

01-components.puml 已将逻辑调用统一为虚线开放箭头依赖，并按主服务、Worker 执行组件、数据配置与外部能力分组；移除与逻辑组件视图不一致的装饰性数据库／存储图元。

依据：§10.4.4 Interfaces、§11.3.4 Encapsulated Classifiers、§11.6.4 Components；[PlantUML 组件图语法](https://plantuml.com/component-diagram)。

## 4. 活动图

### 规范图形与连线

| 图元 | 图形 | 语义 |
| --- | --- | --- |
| 初始节点 | 实心圆 | 开始一条控制流 |
| 动作 | 圆角矩形 | 执行一个行为步骤，名称宜表达行为 |
| 决策节点 | 菱形 | 按条件选择后继路径 |
| 合并节点 | 菱形 | 汇集替代路径，不等待所有路径同时到达 |
| 分叉节点 | 粗线段 | 将控制流分成并行路径 |
| 汇合节点 | 粗线段 | 按同步条件等待并行路径 |
| 活动终止 | 实心圆外套圆 | 结束整个活动 |
| 流终止 | 圈内 X | 只结束当前流 |
| 对象节点／引脚 | 矩形／动作边缘的小方块 | 表达传递的数据对象 |

控制流与对象流使用带开放箭头的实线，守卫条件写为 [条件]，放在分支边靠起点处。动作执行与数据对象流动通过图元及上下文区分，不能简单用线的颜色来定义。应检查导出图是否实际保留守卫的中括号，不能仅凭源码中的箭头标签写法判断。

### 需要特别避免的语义错误

1. 动作有多条输入控制流时存在隐式汇合，默认需要这些输入都提供令牌。两个替代分支不能直接接入下一动作，应先使用 MergeNode。
2. 动作完成时向全部输出控制流提供令牌，存在隐式分叉。业务选择应明确建模为 DecisionNode，并给出守卫。
3. Merge 与 Join 不可互换：前者承接替代路径，后者同步并行路径。
4. 只在实现确实并行时使用 Fork／Join；多个 Agent 的存在本身不构成并行执行证据。

本项目的可选检查应按以下结构建模：

> 生成产物 → 决策“是否执行检查” → [是] 执行检查 / [否] 跳过 → 合并 → 用户确认 → 下一阶段。

修复循环还需要明确“存在问题”“修复预算尚未耗尽”和继续／退出条件。检查反馈、人类确认和执行失败应按各自实际行为表达。

### 本项目布局约定

- 主线沿一个方向展开；检查分支放主线侧方，修复回环靠外侧。
- 动作名称用“规范化题目”“检查代码”等行为；执行 Agent 可在括号、职责泳道或说明中标明。
- 泳道／活动分区采用统一分类维度。按角色划分时不要混入一个阶段名；按阶段分区时应明确其含义。
- 十 Agent 的完整控制流如过于密集，采用主活动与细化活动的层次化表达，保留角色映射；不能为横向排版省略决策、合并等必要控制节点。

### 本次修正

02-agent-activity.puml 已压缩为五阶段横向概要：决策分支与合并用 if/endif 表示；可选检查和各阶段 Agent 通过动作名称归纳，渲染修复回路带预算条件，避免把所有 Agent 子流程展开成纵向长图。

本图源码采用 PlantUML 经典活动语法，使条件节点直接渲染为菱形；依据：§15.2.4 ActivityEdges、§15.3.4 Control Nodes、§15.5.3.1 Executable Nodes、§15.6.4 Activity Partitions、§16.2.4 Actions；参见 [PlantUML 活动图语法](https://plantuml.com/activity-diagram)。

## 5. 领域类图

### 规范图形与连线

- 类使用矩形分区表示名称、属性、操作等内容，可以隐藏与本图无关的分区。
- 属性宜以“名称 : 类型”表达，必要时加可见性、多重性、默认值和约束。
- 关联使用实线；角色名与多重性放在关联端附近；关系名放在连线附近。OMG UML 2.5.1 §11.5.4 允许关联线由一个或多个相连线段构成，并说明线段几何没有关系语义；标准没有专门规定曲线连接，PPT 中采用直线或直角折线更稳妥。
- 1、0..1、0..*、1..* 等多重性各有明确数量含义。
- 若使用聚合／组合，先确定领域的整体与部分关系，菱形画在整体端。

### 本项目布局约定

- 本图定位为领域与持久化概念的关系图，不混画物理表结构、Java 对象引用与业务执行步骤。
- 将任务和任务版本放上方，阶段产物与阶段结果放下方，减少交叉线。
- “任务版本选择阶段产物”可用普通关联及约束表达，注明按任务、阶段与版本号定位。0..5 还应说明每个阶段最多选择一个产物。
- 属性各占一行，version 与 baseVersion 分别写出；不要用“version / baseVersion”代替两个属性的建模说明。
- 先使用有充分依据的普通关联；只有明确整体／部分语义时才使用菱形。

### 本次修正

03-version-model.puml 已移除缺少生命周期依据的聚合菱形，改用带多重性的普通关联；补全版本、阶段产物和阶段结果属性，并用注释说明阶段指针和产物复用约束。

依据：§9.2.4、§9.5、§11.5.4；[PlantUML 类图语法](https://plantuml.com/class-diagram)。

## 6. 部署图

### 规范图形与连线

- Node：立体节点框，表示可承载部署制品的计算资源。
- Device：节点图形配 «device»，用于硬件设备。
- ExecutionEnvironment：节点图形配 «executionEnvironment»，用于 JVM 等软件执行环境。
- Artifact：带 «artifact» 的矩形，或标准文档图标，表示 JAR、脚本等制品。
- CommunicationPath：节点间的关联式通信路径。本项目采用无箭头实线，标注 HTTP、JDBC 等协议。
- Deployment：制品指向部署目标的虚线依赖，可标注 «deploy»；将制品画在部署目标内部也可表达部署。
- Manifestation：制品指向它所体现的组件等模型元素的虚线开放箭头，标注 «manifest»。

### 本项目布局约定

- 区分主机、JVM／工具执行环境和 JAR。Worker 进程／运行环境与 Worker JAR 不使用同一个 Artifact 方框混写。
- 例如主服务节点内嵌 JVM 环境，JVM 中放 study.jar；Worker 节点中相应放 worker.jar。
- 基础服务主机分布不确定时，保留清楚命名的外部节点／执行环境，不推测共用一台物理设备。
- “共享基础服务”可作为视觉分组，但通信路径必须落在实际节点或部署目标上，不连到无模型含义的装饰框。
- 通信路径与“上传／下载的先后次序”分开；后者在时序图中说明。

### 本次修正

04-deployment.puml 已区分 Device、ExecutionEnvironment 和 Artifact：主服务与 Worker JAR 放入对应执行环境，Manim／Chromium 单独作为执行环境；节点之间使用无箭头实线通信路径并标注协议，不把领取或提交流程混入部署关系。

依据：§19.2.4 Deployments、§19.3.4 Artifacts、§19.4.3～19.4.4 Nodes；[PlantUML 部署图语法](https://plantuml.com/deployment-diagram)。该工具页面支持的形状集合大于 UML 核心记法。

## 7. 时序图

### 规范图形与连线

| 元素 | 记法 | 说明 |
| --- | --- | --- |
| 生命线 | 参与者头部＋竖直生命线 | 可用“角色名 : 类型”标识，竖线可为虚线 |
| 执行规格 | 生命线上的细长矩形 | 表示一次执行区间，根据需要显示 |
| 同步消息 | 实线＋实心箭头 | 调用方等待调用完成 |
| 异步消息 | 实线＋开放箭头 | 发送方不因该消息等待返回 |
| 回复消息 | 虚线箭头 | 可使用开放或实心箭头，统一图内风格 |
| 组合片段 | 左上角带操作符的矩形框 | alt、opt、loop、par、critical 等各有特定含义 |
| 交互引用 | 带 ref 标识的引用框 | 表示 InteractionUse，引用另一个交互 |

alt 采用带 [条件] 的替代操作数，opt 表示可选执行，loop 表示循环，par 表示并行交错，ref 引用另一个交互。它们不能仅作为任意文字分组框使用。

### 本项目布局约定

- 时间总体从上向下推进；垂直距离不自动表示精确耗时。参与者按本场景的交互关系排序，消息尽量水平。
- Worker A、任务存储／提交服务、Worker B、归档服务等角色保持抽象层级一致。
- 消息名表达一个调用或结果，长段落解释放注释。
- 租约有效／失效采用显式条件，错误拒绝若是调用回复，应画虚线回复，不能用红色实线代替消息类型。
- 可以显示激活条帮助解释同步调用；不为装饰而把所有生命线从头激活到尾。
- 数据库事务不自动等同于 UML critical。critical 约束所覆盖生命线的事件交错；若只标识 begin／commit 范围，使用实际调用、注释或引用细化交互，并明确任务行范围。

### 本次修正

05-failover-sequence.puml 已统一使用参与者生命线，将旧令牌拒绝表达为虚线回复；接管后的提交事务使用 critical 组合片段，明确租约、令牌、版本和阶段校验，外部模型／渲染／上传仍位于短事务之外。

依据：§17.3.4 Lifelines、§17.4.4 Messages、§17.6 Fragments、§17.8 Sequence Diagrams；[PlantUML 时序图语法](https://plantuml.com/sequence-diagram)。

## 8. 规范要求与 PPT 排版建议的边界

以下是本项目的展示约定，不宣称为 OMG 的强制版式：

1. 每页一张主图，每张图回答一个问题，细节通过分图或附录展开。
2. 可采用左到右或上到下布局；优先保持一致的阅读方向，循环沿外侧返回。
3. 正交线与折线并非绝对要求。减少交叉、折返及不必要弯曲，任何线都不穿过节点、标题、多重性和消息文本。
4. 图元对齐，等语义图元尺寸一致，相关元素靠近，线上的名称贴近所属关系。
5. 类与组件使用易区分的标准矩形记法，活动动作保留圆角。弱化阴影、渐变和装饰色，保证黑白打印仍能辨认语义。
6. 字体以最终幻灯片显示大小判断，图中主要标签尽量不小于 18 pt；图太密时拆分，保留必要的决策、合并和条件。
7. 自动布局只负责排版。渲染完成后同时核对模型语义、源码记法和图面可读性。

OMG 规范 §6.4 说明示例在字体、线宽等样式细节上可以不同。图的横竖方向、颜色与留白不应和符号的规范语义混为一谈。

## 9. 重画前的检查顺序

1. 明确视图：逻辑结构、业务行为、领域关系、物理部署或具体交互。
2. 列出模型元素：组件、接口、动作、控制节点、类、执行环境、制品或生命线。
3. 为每条关系选定语义，再确定虚实线、箭头、菱形、守卫和多重性。
4. 根据代码核对选择、循环、确认、修复、租约和版本关联。
5. 控制一张图的复杂度，选择清晰的主方向与分层。
6. 最后才调整样式、字体、间距与导出格式。
